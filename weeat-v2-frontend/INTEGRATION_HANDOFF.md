# WeEat AI — Integration Readiness Audit

Audit date: 31 October 2026. Repository: `hackathon_weeat`. Frontend: `weeat-v2-frontend/`. Branch: `feature/frontend`.

**Assessment: the approved frontend is ready for coordinated API integration, but live end-to-end readiness is blocked.** HTTP wiring exists for the nine agreed operations. Real Firebase sign-in, backend identity mapping, a working analysis/Ask service, and confirmed-address onboarding must be resolved before the principal journey can run against real services. Live Map/location, Memory, and history restoration have no agreed transport contracts. They must not be represented as completed live integrations.

The audit inspected frontend code and preparation contracts only. No backend implementation, deployed API, Gemini project, Firebase project, credentials, or real-user data was inspected. “Implemented” below means a frontend path exists, not that a backend has been verified. Intercepted HTTP tests use synthetic responses and authentication.

## Shared transport, authentication, and schema rules

`VITE_API_BASE_URL` is the backend origin/prefix **before** `/api`, trimmed with trailing slashes removed. Requests use `Accept: application/json`; bodies additionally use `Content-Type: application/json`. Private calls obtain a fresh token using `AuthUser.getIdToken()` and send `Authorization: Bearer <token>`. There is no cookie-auth configuration, token exchange endpoint, automatic retry, streaming protocol, or live-to-mock fallback.

The fetch transport uses an AbortController with a 15-second timer and propagates caller cancellation. A hanging token-provider promise is not itself raced against that timer: abort stops fetch, but cannot settle a never-resolving `getIdToken()`. The auth adapter must bound/reject token acquisition; frontend transport hardening is a follow-up if that cannot be guaranteed.

Errors use `{ "error": { "code": "...", "message": "..." } }` with an appropriate HTTP status. The client retains code/message/status; `errorKey()` localizes known codes. Arbitrary backend codes can currently appear as raw code text, so the backend must supply its error-code catalog for frontend mapping. Network failures show a generic error; timeout becomes `TIMEOUT`. Malformed successful JSON is `INVALID_RESPONSE`; non-success without a usable JSON envelope is `HTTP_ERROR`. A save failure never produces local success. A timed-out mutation may still commit server-side, so backend idempotency and subsequent reconciliation are essential.

All private endpoints must verify Firebase tokens and derive ownership server-side. A user ID in a response or path is not authorization. The frontend's ownership rejection is defense in depth.

## Identity, persistence, and lifecycle acceptance

The canonical frontend key is `JSON.stringify([String(user_id), String(video_id), String(restaurant_id)])`. Detail routes URL-encode that tuple; save/edit HTTP paths encode video and restaurant separately, while the bearer identity supplies the user. IDs must be stable and remain strings for video/restaurant; a numeric `is_saved` is mandatory. A single restaurant ID must not stand for rows belonging to other sources/users.

Required sequence: analyze an owned source → obtain multiple unsaved rows (`0`) → explicitly PUT one/all → receive `1` → reload Library to see durable state → DELETE one tuple → receive `0` while preserving siblings and the shared video/transcript. Re-analysis preserves an independently saved tuple. Do not auto-save every extracted result or retrieve unsaved rows for Ask.

Backend persistence must enforce an equivalent owner/video/restaurant uniqueness constraint and authorization, transactionally store source/rows, and apply save/unsave idempotently. Exact database schema/migrations belong to the backend owner; none were created or inspected here. A client timeout is not proof of rollback. Repeated analysis, duplicate model detections, repeated saves, and concurrent users need server tests as well as client guards.

## Prioritized integration sequence

1. **P0 — freeze identity and transport.** Backend/auth/frontend agree UID mapping, base URL, CORS, errors and synchronous timeout expectations. Exit: public categories and authenticated profile/empty Library work for a real new user.
2. **P0 — unblock onboarding.** Register Firebase adapter; supply jointly approved confirmed-address service. Exit: sign-in → selected home → PATCH profile → reload ready state, without fixtures.
3. **P0 — analysis and saving.** Connect Gemini-backed `/api/analyze`, then tuple-safe PUT and Library hydration. Exit: multiple genuinely extracted unsaved places → save one/all → durable reload, no duplicates.
4. **P1 — persistence and sources.** Validate PATCH/DELETE, sibling preservation, source/transcript hydration and complete snapshot semantics; fix frontend reconciliation after agreement. Exit: reload and cross-device state match database.
5. **P1 — grounded Ask.** Verify owner-scoped retrieval, citations, session continuation, latency and failures; separately agree history restoration. Exit: saved-only answers with real source cards and no cross-user retrieval.
6. **P1 — approved missing services.** Jointly define and integrate location/Map/route and Memory; detours only if explicitly added by agreement. Exit: validated service semantics replace blocked states without redesign.
7. **Release gate.** Backend and frontend jointly run staging acceptance, inspect production bundle/config, record actual provider/device evidence, and retain a working explicitly labeled development demo. This audit does not authorize a push, merge, or deployment.
